# Known limitations and remaining acceptance gates

This is a production-oriented hardening candidate, **not an unconditional production-readiness claim**.

1. **Live integration:** no production deployment, Telegram send or account OAuth login was performed during this upgrade. Obtain an authorized test bot/channel, public HTTPS domain and real IdP configuration; verify getMe/getChatMember, intended media/slideshow/emoji contexts and ChatGPT/Codex linking.
2. **Telegram coverage:** all 185 pinned Bot API methods have registry/transport coverage, not live behavioral certification. Telegram prose constraints, bot permissions, chat type and client eligibility remain authoritative. MTProto, multi-account user sessions, Telegram Ads, arbitrary history and native reach analytics are not implemented.
3. **Agent runtime:** deterministic durable workflows exist; an internal autonomous LLM loop, model/provider billing and approval-wait resumption driven by an LLM do not. External agents use the same gateway. No orchestration framework was added without a concrete need.
4. **OAuth:** resource-server JWT verification exists; an external authorization server supplies OAuth login/PKCE/consent/registration/refresh. No opaque-token introspection. Cloud ChatGPT cannot use a localhost endpoint. Client-specific availability depends on account/workspace configuration.
5. **UI:** responsive English administration console and generic method editor, not specialized visual editors for every Bot API type. No full localization, accessibility certification, animated emoji player or native Telegram rendering emulator. Keyboard preview is structural; callback-response automation is not implemented.
6. **Access model:** one operator/owner credential and per-agent grants. No teams/SSO owner portal/MFA, resource sharing/ownership transfer UI or in-place grant policy edits. Create a new reviewed grant and revoke the old one. Emoji catalog and safe DB metadata are shared installation resources.
7. **Credentials:** upgraded installations retain optional legacy static agent/reader mode for compatibility; disable it explicitly after migration. Owner key is operator-managed and powerful. New grants expire; local revocation cannot recall an already in-flight Telegram request.
8. **Delivery:** no exactly-once guarantee. Uncertain requests require owner reconciliation. Native albums/steps may have partial effects; automatic rollback is not assumed. Snapshot restoration can lose post-backup idempotency evidence. Same-timestamp operation pagination is not snapshot-stable.
9. **Operations:** no actual Ubuntu VPS was provisioned. Docker/Compose and migration CI are the installation evidence. The same-revision rollback drill does not prove arbitrary cross-release downgrade compatibility. Rollback needs the old Git commit/build dependencies. `.env` and off-site encrypted backups remain operator responsibilities.
10. **Security/scale:** no independent penetration test/load benchmark. The shared database queue is appropriate for current scope, not proven high-volume SaaS. Media MIME is declared; no antivirus or separate renderer sandbox. Unauthenticated edge traffic needs infrastructure rate limits. Only the five security-boundary modules currently have a mypy gate; this is not whole-project strict typing.
11. **Observability:** optional OTLP exporter tested in-memory, no collector deployed. Application correlation does not implement full cross-process W3C tracing. Persisted audit identifies REST/domain actions rather than every MCP tool name. One global heartbeat indicates some worker is alive. Non-HTTP audit, updates/media and idempotency records are retained; archival remains operator-managed.
12. **Protocol:** 42 tested tools with typed inputs and bounded structured JSON; some result dictionaries are intentionally open schemas and image output is a content block. Tool errors can be structured `{ok:false}` even with MCP `isError=false`; clients must inspect both. `/v1` remains the REST prefix; `/api/v1` is not implemented.
