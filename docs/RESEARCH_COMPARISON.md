## Official specification evidence

- [Telegram Bot API](https://core.telegram.org/bots/api): preserve pinned 10.3 contracts; methods do not grant account/channel permissions.
- [Telegram API](https://core.telegram.org/api): MTProto is a separate account/session integration, not an alternative name for Bot API.
- [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization): resource discovery, audience validation and authorization at each request.
- [MCP security](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices): confused-deputy/token-passthrough defenses and untrusted content.
- [MCP transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports): Streamable HTTP, origin validation and transport lifecycle.
- [OpenAI authentication](https://developers.openai.com/plugins/build/auth): OAuth resource metadata, authorization-code/S256 PKCE and client registration belong to the authorization server. Clients can use CIMD, DCR or predefined clients subject to their documented support.
- [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli): HTTP bearer environment variables and OAuth setup are distinct options; ChatGPT connection does not inherit a Codex bearer configuration.

## Build versus adopt

Keep the official MCP SDK, SQLAlchemy/Alembic/PostgreSQL queue and modular monolith. Add an external-issuer OAuth resource server; do not invent an authorization server, login UI, refresh-token store or dynamic-registration proxy. Retain the REST service as the shared gateway and carry each MCP caller's resource-scoped identity into that same service. Use explicit, deny-by-default scope/method/channel policies rather than a generic agent escape hatch. No Redis, Celery, Temporal, LangGraph, n8n or MTProto dependency is justified for this iteration. Optional OpenTelemetry uses the standard SDK; no content attributes. Revisit orchestration only with measured queue/backlog or internal model-runtime requirements.
